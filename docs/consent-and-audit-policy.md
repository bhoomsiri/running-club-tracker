# นโยบาย consent + audit — ข้อมูลไหนอยู่บนฐานอะไร

เอกสารสำหรับ **DPO / นิติกร** และสำหรับคนที่จะแก้โค้ดส่วนนี้ต่อ · อ้างอิงพฤติกรรมจริงบน `main`

คำถามที่เอกสารนี้ตอบ: **"สมาชิกถอนความยินยอมแล้ว เกิดอะไรขึ้นบ้าง"** — คำตอบไม่เหมือนกันทุกข้อมูล
เพราะแต่ละอย่างเก็บด้วย**ฐานทางกฎหมายคนละตัว** ไม่ใช่ความไม่สอดคล้อง

---

## หลักการเดียวที่ใช้ตัดสินทุกข้อ

> **consent คุมสิ่งที่ "ชมรม" ทำกับข้อมูล — ไม่ใช่สิทธิที่ "เจ้าตัว" จะดูข้อมูลของตัวเอง**

การถอนความยินยอมจึงหยุด**การประมวลผลฝั่งชมรม** แต่ไม่ตัดสิทธิเข้าถึงข้อมูลตัวเอง (PDPA ม.30)
และ **ไม่ลบข้อมูล** — ยินยอมใหม่เมื่อไหร่ ชมรมกลับมาใช้ได้เมื่อนั้น

---

## ตารางตัดสิน

| ข้อมูล | ฐานทางกฎหมาย | เจ้าตัวดูเอง | admin ดูของคนอื่น | ถอนยินยอมแล้ว | audit |
|---|---|---|---|---|---|
| **น้ำหนัก / ส่วนสูง / ชีพจร / ความดัน** (`health_record`) | ความยินยอม (ม.26) | เห็นเสมอ | ได้ ถ้ายินยอม active | admin **ปิด** · เจ้าตัวยังเห็น | ✅ ทุกครั้งที่ admin เปิด |
| **แบบคัดกรอง PAR-Q** (`screening`) | ความยินยอม (ม.26) | เห็นเสมอ | ได้ ถ้ายินยอม active | admin **ปิด** · เจ้าตัวยังเห็น | ✅ ทุกครั้งที่ admin เปิด |
| **ผู้ติดต่อฉุกเฉิน / เบอร์ / เพศ / วันเกิด** (`member`) | **ประโยชน์ด้านความปลอดภัย (ม.24)** | เห็นเสมอ | **ได้เสมอ** | **ไม่ปิด** | ✅ ทุกครั้งที่ admin เปิด |
| **ระยะทาง / เวลา / แคลอรี่ / ก้าว / แต้ม** (`run_entry`, `points_ledger`) | การเข้าร่วมกิจกรรมของชมรม | เห็นเสมอ | ได้ (ไม่ใช่ข้อมูลอ่อนไหว) | ไม่เกี่ยว | ❌ ไม่ต้อง |
| **ชื่อ + ระยะสะสมบนตารางอันดับ** | การเข้าร่วมกิจกรรม (แจ้งให้ทราบ ไม่ใช่ขอความยินยอม) | — | ทุกคนในชมรมเห็น | **ไม่ปิด** | ❌ |

---

## ทำไมผู้ติดต่อฉุกเฉินถึงไม่ผูกกับ consent สุขภาพ

เบอร์ผู้ติดต่อฉุกเฉินถูกเก็บเพื่อ **โทรตามญาติตอนสมาชิกล้มระหว่างวิ่ง** ถ้าเอาไปผูกกับความยินยอม
เรื่องข้อมูลสุขภาพ จะได้ผลลัพธ์ที่กลับหัวกลับหาง:

> สมาชิกถอนยินยอมเพราะไม่อยากให้ชมรมเก็บน้ำหนัก → ชมรมโทรหาญาติไม่ได้ตอนเขาหมดสติ

ซึ่งเป็นการเอาข้อมูลออกไปจากมือชมรม **ในนาทีที่มันถูกเก็บมาเพื่อสิ่งนั้นพอดี** ฐานของมันจึงเป็น
ม.24 (ประโยชน์โดยชอบด้วยกฎหมาย/ความปลอดภัยของเจ้าของข้อมูล) ไม่ใช่ ม.26

**ไม่ gate ≠ ไม่ตรวจสอบ** — การเปิดดูยังถูกบันทึก `audit_log` ทุกครั้งพร้อมชื่อคนเปิด ชมรมจึง
แสดงได้ทั้งว่า *เปิดตอนไหน* และ *ไม่ได้เปิดตอนไหน*

## ทำไมแบบคัดกรองถึงผูก

PAR-Q ถามว่าเคยมีโรคหัวใจไหม เจ็บหน้าอกไหม กินยาความดันอยู่ไหม — นั่นคือ**ประวัติสุขภาพ**
ไม่ต่างจากน้ำหนักในแง่ ม.26 จึงต้องอยู่บนฐานเดียวกัน

> เดิมช่องนี้เปิดอยู่: ถอนยินยอมแล้ว `/admin/members/{id}/health` ตอบ 403 แต่
> `/admin/members/{id}/screening` ยังอ่านคำตอบได้ ทำให้การถอนมีความหมายน้อยกว่าที่เห็น
> ปิดแล้วเมื่อ 29 ส.ค. 2026

---

## โครงสร้างโค้ดที่บังคับกฎนี้

ฐานที่ต่างกันถูกเขียนลงใน **โครงสร้าง** ไม่ใช่แค่คอมเมนต์ — port แยกกัน:

```
ScreeningViewUnitOfWork   members · screenings · consents · audit · clock   ← มี consents
ContactViewUnitOfWork     members ·              audit · clock              ← ไม่มี consents
HealthUnitOfWork          members · health · consents · audit · clock       ← มี consents
```

`ViewMemberContact` **ไม่มี consent repository ให้เรียกด้วยซ้ำ** ถ้าใครมาเติม gate ทีหลังจะต้อง
แก้ port ก่อน ซึ่งเป็นจุดที่บังคับให้อ่านเหตุผลนี้ก่อน

การอ่านทุกทางที่แตะข้อมูลอ่อนไหวเขียน `audit_log` **ก่อน** คืนข้อมูล และ commit พร้อมกัน —
การเข้าถึงที่บันทึกไม่ได้ต้องไม่เกิดขึ้น

## การส่งออก Excel (`/admin/export`)

ใช้กฎเดียวกันเป๊ะ ต่อสมาชิกรายคน: ชีตสุขภาพ + แบบคัดกรอง **ข้ามคนที่ถอนยินยอม** ·
ชีตข้อมูลติดต่อ **ไม่ข้าม** · ทุกคนที่ข้อมูลอ่อนไหวหลุดออกไปได้ `audit_log` เป็นรายคน

> **คำถามเปิดสำหรับ DPO:** bulk export ควรมีคอลัมน์ผู้ติดต่อฉุกเฉินไหม (data minimisation) —
> การโทรตามฉุกเฉินเกิดทีละคนผ่านหน้า `/admin/members/{id}/contact` ที่มี audit อยู่แล้ว
> การมีทั้งชมรมอยู่ในไฟล์เดียวเป็นคนละความจำเป็นกัน · ยังไม่ตัดสิน

## สิ่งที่ยังไม่มี (อย่าให้ถ้อยคำ consent สัญญาเกินนี้)

- ❌ **purge job** — `health_record.retention_until` ถูกเขียนไว้แต่ยังไม่มีอะไรอ่าน
  ผู้ดูแลลบเองเมื่อครบกำหนด ซึ่งเป็นสิ่งที่ข้อความ consent v2 เขียนไว้ตรงตามความจริง
- ❌ **use case ลบข้อมูลตามคำขอ** — สมาชิกต้องติดต่อผู้ดูแล (มีสคริปต์
  `scripts/delete_test_member.py` เป็นแนวลำดับการลบที่ถูกต้อง)
- ❌ **opt-out ตารางอันดับ** — DPO รับได้กับการเป็น "แจ้งให้ทราบ" ถ้าเปลี่ยนใจต้องมี flag
  ที่ member + use case รองรับ ไม่ใช่แก้ถ้อยคำ

เมื่อสร้างสองอย่างแรก **ค่อยแก้ถ้อยคำ consent ให้สัญญามากขึ้นได้ และต้องขยับ `CONSENT_VERSION`**
— ซึ่งแปลว่าไล่ถามสมาชิกที่ยินยอมไปแล้วทุกคนใหม่ ดู `backend/app/config.py`
